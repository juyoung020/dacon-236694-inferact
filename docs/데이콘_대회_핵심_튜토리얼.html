AI 코딩 에이전트의 다음 행동을 맞혀라

세션의 한 순간을 보고, 에이전트가 다음에 취할 행동을 14개 중 1개로 예측하는 다중분류 문제. 이 문서는 코드 대신 "무엇을 · 왜 · 어떻게" 를 순서대로 정리한 개념·액션 플랜임.

뭘 맞힘AI 에이전트의 다음 행동 1개 (14개 클래스)
점수Macro-F1 — 소수 클래스도 똑같이 중요
제출코드+모델 zip / 오프라인 · 추론 10분 · 1GB · T4 GPU
주력 무기피처(history·meta) + LightGBM + GroupKFold
점수 올리기불균형 대응(class_weight) + threshold 튜닝 + 앙상블
안 씀LangChain / QLoRA / 대형 LLM (제약·불필요)
🧭 이 문서 읽는 법
1~3장은 개념(뭘 맞히나, 데이터가 뭐냐, 꼭 아는 용어). 4장이 핵심 — 대회 완주까지 단계별 할 일을 "① 무엇을 ② 왜 ③ 주의점"으로 정리함. 5~7장은 점수 올리기·함정·체크리스트. 위→아래로 그냥 쭉 읽으면 됨.

1 대회 한눈에

⚠️ 오해부터 풀기
이 대회는 에이전트를 만드는 게 아님. 이미 찍힌 로그로 분류기를 학습하는 순수 지도학습임. 그래서 LangChain/LangGraph(에이전트 프레임워크)도, QLoRA·대형 LLM도 안 씀 — 제약에 막히고 불필요함. 정석은 고전 ML + 작은 인코더.

실행 제약 — 못 지키면 0점

제약값
추론 시간≤ 10분 (실제 평가셋 30,000건)
패키지 설치≤ 10분
제출 용량≤ 1GB
인터넷오프라인 — 모델·라이브러리 다 zip에
하드웨어T4 GPU 16GB / 3 vCPU / 12GB RAM

제출 형식은 예측 CSV가 아니라 추론 코드+모델 zip임 → 서버가 오프라인으로 직접 돌림. 그래서 "어떤 모델을 쓰냐"만큼 "제약 안에서 돌게 만드느냐"가 중요.

🎯 출제 의도 — 왜 "작은 모델"이 정답인가 (대회안내 '주제선정 배경'에서 캔 힌트)
주최측이 원하는 건 "LLM을 부르기 전에 다음 행동을 빠르게 결정하는 경량·고속 라우터(router)"임. 실제 에이전트는 무거운 LLM 앞에 가벼운 의사결정 모델을 둬 행동을 먼저 분기하는데, 이 대회가 바로 그 모델을 만드는 것.
  • 제약(10분·1GB·오프라인·T4)은 임의가 아님 — 실시간 라우터를 흉내 낸 것. 대형 LLM은 출제 의도 자체에 어긋남 → 작은 모델이 정답.
  • 주최측이 "정확성뿐 아니라 속도·효율도 핵심"이라 못 박음 → 경량화할수록 앙상블 여유↑.
  • 정답 신호는 세션 상태(메타·이력) 안에 있음 = LLM 없이 뽑는 값싼 피처가 핵심.

일정: 예선 07.01~07.15 · 예선평가 07.17 · 예선발표 07.27 · 본선 08.11

2 데이터가 뭐냐

한 샘플(JSON 한 줄)은 세 부분으로 구성됨. 이 직후에 에이전트가 한 행동이 정답임.

필드뜻

history직전까지 user ↔ action 교대 이력 (직전 action·result_summary가 핵심)
session_meta요금제·잔여토큰·turn_index·git_dirty·last_ci_status·open_files·언어비율
🎯 정답을 결정하는 강한 신호 3개
① current_prompt ("테스트 돌려봐" → run_tests) · ② 직전 action + result_summary ("CI failed" → edit_file/run_tests) · ③ session_meta 상태 (git_dirty, last_ci_status) → 이 셋을 피처로 살리는 게 4장 액션 플랜의 뼈대임.

3 꼭 아는 핵심 개념

대회에 직접 쓰이는 것만 추림. 각 개념을 "뭐임 → 왜 → 이 대회 적용" 순으로 쉽게. 수식은 최소.

📝 TF-IDF (텍스트→숫자)

모델은 숫자만 먹음. TF-IDF는 이 문서에서만 특별히 자주 나오는 단어에 높은 점수를 줌. "the"처럼 흔하면 자동 감점.

이 대회: 사용자 발화를 word(1~2) + char(3~5) n-gram으로 숫자화. 코드·파일명(run_tests, .toml)이 많아 글자 단위(char)가 잘 먹음.

🧩 피처 엔지니어링

원본에서 모델이 배우기 좋은 새 변수를 사람이 만들어 주는 것. 여기가 진짜 점수.

이 대회: 베이스라인은 current_prompt만 씀 → 직전 action, result_summary(성공/실패), git_dirty, CI상태, 턴수 같은 history·meta 신호를 피처로 살리면 바로 앞섬.

⚖️ Macro-F1 & 불균형

클래스별 F1을 단순 평균(1/14씩 동등). 소수 클래스도 다수와 똑같이 한 표.

대응: class_weight='balanced'(소수 클래스 오차에 큰 벌점) · threshold 튜닝. 이게 없으면 소수 클래스를 다 틀려 점수가 낮음.

🌳 LightGBM

결정트리를 오차 보정하며 쌓는 부스팅 모델. 표(수치+범주) 피처에 강하고 빠름 → CPU로도 10분 내. 이 대회 메인 무기.

빠른 비법: leaf-wise 성장 · GOSS · EFB. 튜닝 적어도 성능 좋아 가성비 1등.

🚨 세션 누수 & GroupKFold — 우승의 90%

한 세션(sess_..._028750)은 여러 step으로 쪼개져 있고 서로 매우 비슷함. 랜덤 K-fold를 쓰면 같은 세션이 train/val에 섞여 모델이 세션을 통째로 암기 → 검증 점수가 가짜로 높게 나옴(일반화 아님). 반드시 같은 세션은 통째로 한쪽 폴드에 넣어야 함.

flowchart TB
    subgraph BAD[랜덤 KFold 세션 누수 X]
        A1[세션A step1,3,5] --> TR1[Train]
        A2[세션A step2,4] --> VA1[Val]
    end
    subgraph GOOD[GroupKFold 세션 통째로 O]
        B1[세션A 전체] --> TR2[Train]
        B2[세션B 전체] --> VA2[Val]
    end

세션키 = id에서 -step 앞부분. 불균형+그룹 둘 다 잡으려면 StratifiedGroupKFold(그룹 유지 + 클래스 분포 균등)가 최적.

🎚️ threshold 튜닝 — 저비용 점수 상승

확률 최댓값(argmax)만 쓰면 소수 클래스는 확률이 늘 낮아 거의 안 뽑힘. 클래스별 가중치를 곱한 뒤 argmax 하면 소수 클래스가 뽑히기 쉬워져 macro-F1이 오름 — 모델은 그대로라 공짜에 가까움. 단, 소수 클래스 가중치를 너무 키우면 남발(병적 해)해서 오히려 떨어짐 → 검증 데이터에서 신중히.

왜 대형 LLM/QLoRA를 안 쓰나
7B는 4bit로도 ≈4GB → 1GB 초과, 3만 건 생성추론 → 10분 초과. 게다가 과제는 분류라 생성형이 불필요함. deberta-v3-base 같은 작은 인코더(수백MB)면 다 통과하고 정확도도 안정적.

🧰 손에 쥘 도구(라이브러리)

pandas·numpy 표·배열 scikit-learn TF-IDF·CV·지표 scipy 희소행렬 결합 lightgbm 메인 모델 joblib 모델 저장

선택(상위권): transformers·torch(DeBERTa) · onnxruntime(추론 가속) · xgboost/catboost(앙상블).

4 무엇을 해야 하나 — 단계별 액션 플랜

대회 완주까지의 순서. 각 단계는 ① 무엇을 · ② 왜 · ③ 주의점으로. 이 흐름만 따라가면 제출까지 감.

flowchart TD
    A[1 데이터 열어보기 EDA] --> B[2 피처 만들기 features.py]
    B --> C[3 텍스트 숫자화 TF-IDF + 표 결합]
    C --> D[4 검증 설계 StratifiedGroupKFold]
    D --> E[5 학습 LightGBM]
    E --> F[6 점수 확인 OOF Macro-F1]
    F --> G[7 threshold 튜닝]
    G --> H[8 전체 재학습 bundle 저장]
    H --> I[9 오프라인 리허설]
    I --> J[10 zip 제출]
⚠️ 관통하는 대원칙 하나
피처 만드는 함수는 features.py 한 곳에 두고 학습과 제출이 똑같이 불러 쓰게 함. 복붙 두 벌을 두면 전처리가 어긋나 점수가 무너짐. (아래 2·8·9단계 전부 이걸 전제로 함)
1데이터를 직접 열어본다 (EDA)
무엇을표만 보지 말고 Day 1에 직접 로드해서 클래스 분포·history 길이·세션당 step 수·빈 프롬프트 비율을 눈으로 확인.
왜불균형이 얼마나 심한지, 이력이 비어 피처를 못 쓰는 샘플이 얼마나 되는지 알아야 이후 피처·검증 설계가 쉬워짐.
주의직전 action → 정답 분포표를 만들어 보면 강한 규칙(예: apply_patch 다음 run_tests)이 바로 보임 → 그게 곧 강피처.
2피처를 만든다 (history·meta 살리기)
무엇을한 샘플 → 숫자·범주 변수로 바꾸는 함수를 features.py에 작성. 텍스트(current_prompt+과거 user 발화), 직전 action, result_summary의 성공/실패, git_dirty·last_ci_status·turn_index, action별 등장 횟수, 프롬프트 키워드 유무 등.
왜베이스라인은 current_prompt만 씀. history·meta를 피처로 살리는 순간 바로 앞섬 — 여기가 점수의 핵심.
주의세션키(-step 앞부분)도 이때 같이 뽑아 둠 — 4단계 검증에서 그룹으로 씀.
3텍스트를 숫자로 바꾸고 표와 합친다
무엇을텍스트는 TF-IDF(word 1~2 + char 3~5)로, 범주는 one-hot, 수치는 그대로 → 가로로 이어붙여(hstack) 하나의 입력 행렬로.
왜모델은 숫자만 먹음. 텍스트 신호(무엇을 시켰나)와 표 신호(상태가 어떤가)를 한 판에 모아야 함께 학습됨.
주의TF-IDF는 학습 fold에서만 fit하고 검증엔 transform만. 전체로 fit하면 누수.
4검증을 제대로 설계한다 (세션 누수 차단)
무엇을StratifiedGroupKFold(5분할)로 나눔. 그룹 = 세션키 → 같은 세션은 통째로 한쪽에만.
왜랜덤 분할이면 같은 세션이 train/val에 섞여 점수가 가짜로 뻥튀기됨. 여기서 실패하면 이후 개선이 전부 착시임. 우승의 90%.
주의CV 점수와 리더보드 점수를 늘 같이 기록 → 벌어지면 누수 의심.
5모델을 학습한다 (LightGBM)
무엇을폴드마다 LightGBM 학습. class_weight='balanced'(불균형), early stopping(과적합·시간 낭비 방지), random_state(재현성) 꼭 챙김.
왜표+희소 텍스트 피처에 강하고 빠름 → 제약(10분) 안에서 안정적으로 좋은 점수.
주의학습률은 낮추고 트리 수는 늘리되 early stopping으로 자동 멈춤 — 이게 정석.
6점수를 확인한다 (OOF Macro-F1)
무엇을각 폴드의 검증 예측(OOF)을 모아 Macro-F1을 측정하고, 클래스별 리포트로 어떤 클래스가 약한지 확인.
왜제출 안 하고도 내 개선이 진짜인지 판별하는 기준. 약한 소수 클래스가 곧 점수 병목.
주의어떤 클래스끼리 헷갈리는지(edit_file↔apply_patch 등) 보고 그 경계를 살리는 피처를 2단계에 추가.
7threshold를 튜닝한다 (공짜 점수)
무엇을OOF 확률에 클래스별 가중치를 곱해 argmax → macro-F1이 최대가 되게 가중치를 탐색(한 클래스씩 조정).
왜소수 클래스가 잘 안 뽑히는 걸 완화 → 모델 재학습 없이 macro-F1을 올림(보통 +0.005~0.02).
주의balanced를 이미 썼으면 이중 보정이 될 수 있음 → 가중치를 오히려 1보다 낮춰야 할 수도. 반드시 OOF에서 실측.
8⭐ 전체로 재학습해 bundle을 저장한다
무엇을5단계는 점수 확인용일 뿐. 실제 제출하려면 전체 train으로 다시 학습해서 변환기(TF-IDF·one-hot)·모델·클래스가중치를 한 파일(bundle.pkl)로 저장.
왜이걸 안 하면 제출할 모델 파일 자체가 없음 → 제출 불가. 가장 흔히 빠뜨리는 치명적 단계.
주의트리 수는 5단계 각 폴드의 best iteration 평균쯤으로 고정.
9오프라인 리허설을 한다
무엇을인터넷을 끄고 model/·features.py·script.py만 있는 폴더에서 test 5건으로 실행 → submission.csv가 생기는지 확인.
왜채점 서버는 인터넷이 없음. 여기서 ModuleNotFoundError·다운로드 시도가 있으면 실전 0점.
주의추론이 10분·1GB 안에 드는지 시간·용량도 이때 측정. requirements.txt는 학습 환경 버전으로 고정.
10zip으로 묶어 제출한다
무엇을model + features.py + script.py + requirements.txt를 zip으로 묶어 제출.
왜서버가 zip을 풀고 requirements.txt만 설치한 뒤 script.py를 돌려 채점함.
주의features.py 빠뜨리면 즉시 실패. 제출 CSV는 id,action 컬럼 + sample과 같은 id 순서.
📋 채점 서버가 실제로 하는 일 (공식 코드 제출 가이드에서 캔 힌트)
순서: zip 풀기 → data/·output/ 생성 → pip install -r requirements.txt → python script.py → output/submission.csv 확인.
  • script.py·requirements.txt는 이름 정확히 일치해야 함. zip 이름에 공백·한글 금지.
  • requirements.txt엔 추가로 필요한 것만 — 서버에 이미 깔린 패키지는 빼도 됨('평가' 탭 확인). 다 넣으면 설치 충돌·시간초과 위험.
  • 런타임 에러(크래시·csv 미생성·시간초과)는 제출 횟수 차감 ← 오프라인 리허설이 필수인 이유. (셋업 에러는 차감 없음)
  • 모델·토크나이저·config 전부 model/에 미리 저장 — from_pretrained() 온라인 다운로드 금지.
  • ⚠️ 가이드 체크리스트엔 model/·script.py·requirements.txt만 명시 → 가장 안전한 건 make_features를 script.py 안에 직접 넣기(또는 features.py를 넣되 리허설로 반드시 확인).
✅ 여기까지 = 완주
1~10을 한 바퀴 돌면 리더보드에 점수가 찍힘. 그 다음은 5장 전략으로 같은 뼈대 위에 피처·모델을 얹어 점수를 올리면 됨.

5 점수 올리는 전략

완주 뼈대(4장) 위에 단계별로 얹음. 매 단계 제출해서 리더보드로 실제 확인하는 게 중요.

단계할 것
🥉 Day 1베이스라인 그대로 제출 → 파이프라인이 도는지 확인
🥈 Day 2~4history·meta 피처 + StratifiedGroupKFold + class_weight + threshold → 중상위권 (가성비 최고 구간)
🥇 Day 5~9DeBERTa-v3 파인튜닝 (fp16, max_length≈256, 오프라인 번들)
🏆 Day 10~LightGBM+DeBERTa 가중 앙상블 → threshold 재튜닝

상위권을 가르는 3가지

🔍 고급 피처

전이확률(직전 action일 때 다음 action 확률), result_summary 파싱(테스트 수·수정 파일 수·+/- 줄수), 프롬프트↔open_files 상호작용, TF-IDF→SVD 압축, (오프라인 번들) 문장 임베딩. 숨은 규칙 하나가 모델 여러 개보다 나음.

🧠 작은 인코더

deberta-v3-base를 14클래스로 파인튜닝. 표 정보를 특수토큰으로 문장에 넣어 함께 학습하면 강력. 대형 LLM은 제약에 막히니 base급으로.

🎛️ 다양성 앙상블

LightGBM(표) + DeBERTa(텍스트) 확률을 가중 평균 → threshold 재튜닝. 성능 비슷해도 서로 다르게 틀리는 모델을 섞어야 이득 큼.

📏 신뢰 CV

StratifiedGroupKFold + (여유되면) adversarial validation으로 train/test 분포 이동 점검. public 리더보드 과적합 경계 — 본선은 비공개라 CV를 믿어야 함.

🏆 우승 공식 한 줄
신뢰 CV(StratifiedGroupKFold) + 전이·요약파싱 고급 피처 + (AWP 넣은) DeBERTa & LightGBM 다양성 앙상블 + macro-F1 threshold 최적화 + 오프라인 증류로 10분 안에 우겨넣기.

시험기간이면 Day 1~4(LightGBM 트랙)만 제대로 해도 충분히 승부됨. DeBERTa·앙상블은 시간 남을 때.

6 흔한 함정 (순위 뒤집힘)

  • 세션 누수 — 랜덤 KFold 쓰면 CV가 가짜로 뻥튀기 → 반드시 GroupKFold(세션키).
  • 최종 재학습·저장 빼먹음 — CV만 돌리고 bundle.pkl을 안 만들면 제출할 파일이 없음(4장 8단계 필수).
  • 전처리 불일치 — 피처 함수를 features.py로 분리해 학습·제출이 공용으로 쓰게.
  • 오프라인 잊음 — 서버는 인터넷 없음. 모델·라이브러리 다 zip에.
  • 10분/1GB 초과 — 무거운 모델 탈락. 미리 시간·용량 측정.
  • class_weight 빼먹기 — 소수 클래스 다 틀려 macro-F1이 낮음.
  • 제출 CSV 형식 — id,action 컬럼 + sample과 같은 id 순서.
  • CV↔리더보드 괴리 — CV만 믿지 말고 실제 제출로 검증. 벌어지면 누수 의심.

7 최종 체크리스트

  • ☐ train.jsonl 로드 + EDA + session_key 그룹
  • ☐ 피처 함수(features.py로 분리) — history·meta 살리기
  • ☐ TF-IDF(word+char) + one-hot + 수치 → 결합
  • ☐ StratifiedGroupKFold(5) + LightGBM(class_weight, seed, early stopping)
  • ☐ OOF macro-F1 + 클래스별 리포트로 약한 클래스 확인
  • ☐ threshold 튜닝으로 추가 상승
  • ☐ 전체 재학습 → bundle.pkl 저장 (⭐필수)
  • ☐ 오프라인 리허설(인터넷 끄고 test 5건) → 10분·1GB 확인
  • ☐ features.py+script.py+model+requirements → zip 제출
  • ☐ (여유) 고급 피처 + DeBERTa 파인튜닝 + 앙상블
